# SmartSVG V3.5 — Contrat d'exécution Dual Producer R13

**STATUT : amendement conditionnel adopté seulement après PR de gouvernance R13 fusionnée, CI G0 post-fusion PASS et handoff des deux tâches vérifié.** Tant qu'une condition manque: un seul producteur R12 demeure l'autorité opérationnelle, ou DRAFT-only si les sources divergent. L'autorisation de ce changement provient de la session propriétaire du 19 novembre 2026. Ce document ne suffit pas à activer une tâche.

## Autorités / invariants

1. Lire au début de CHAQUE exécution le vrai HEAD de `main`, `AGENTS.md`, `.automation/READY`, `docs/ROADMAP_PROMOTION_v3_5.md`, `docs/AUTONOMOUS_INTEGRATION_POLICY_V35.md`, `docs/roadmap-v3.5/EXECUTION_STATE.json`, le présent contrat, le contrat complet `PRODUCER_TASK_V35.md`, `MASTER_PRIORISE.md`, `EXECUTION_PLAYBOOK.md` et les PR/CI impactées. Le présent R13 supplante uniquement les clauses R12 **un seul producteur / un seul merger** et la répartition d'activité; toutes les autres obligations demeurent.
2. `AUTONOMOUS_MERGE_V34=DISABLED`, `AUTONOMOUS_MERGE_V35=ENABLED`, `DUAL_PRODUCER_V35=AUTHORIZED` et `R13_MERGE_EXECUTOR=AGENT_B` doivent apparaître exactement une fois chacun dans READY, sans contradiction avec AGENTS et la politique. Sinon: DRAFT-only/NO_MERGE. En cas d'impossibilité de relire l'activation des tâches ou leur prompt: pas d'affirmation que le système dual fonctionne; **B ne fusionne pas**.
3. Préserver 141 exigences V3.3 intégrales, 140 DoD, 24 lots, 80 UX, 437 scénarios, historiques V3.4/V3.3/V3.2 et V21.14.1. Les critères SCN/CST/UXI/CP/SD restent entiers. Une roadmap n'est pas du code, un test de documentation n'est pas une preuve Windows/GPU/Design Space/Cricut.
4. **Exclusions de fusion autonomes inchangées** : aucune PR touchant AGENTS, READY, docs, `.github`, source-releases, fichiers racine, ZIP/binaires, dépendances, packaging, secret, format projet, sécurité/admission, contrôles/permissions, publication/release. Ne pas écrire directement dans main ni outrepasser protections. Les changements de gouvernance passent par une PR séparée explicitement propriétaire et revue hors tâches.
5. Deux agents ont tous deux capacité de lire, concevoir, programmer, tester, corriger, contre-expertiser, ouvrir des PR et préparer des décisions d'intégration. La **capacité d'exécuter la mutation de fusion** est déléguée exclusivement à B après handoff; A demeure autonome pour toutes les autres actions et donne l'avis croisé. Ce choix remplace la nécessité d'une hypothétique file atomique; il n'implique pas que les accès techniques GitHub soient révoqués.

## Identité, rôles, cadence et démarrage
- **A =** tâche existante `6ae27963fd848191a1053dfc486e8eb4`, minute locale H:55, priorité produire les lots utilisateurs selon le chemin critique. Pendant un cycle, peut corriger les PR et contre-expertiser celles de B mais n'exécute plus d'API merge après son handoff R13. Sa cadence et son ID sont conservés.
- **B =** nouvelle tâche d'intégration et production, minute locale H:25, priorité qualifier les PR, diagnostiquer et corriger les régressions, intégrer si admissible; sans PR actionable, développe un micro-lot **indépendant** déjà disponible dans la roadmap. B ne doit pas rester spectateur si une contribution concrète est possible.
- L'ancienne tâche de conception/roadmap reste **désactivée**; aucun travail de TITAN ne doit être modifié.
- **Séquence de passation:** (a) gouvernance revue et fusionnée hors automations, CI exacte et G0 push PASS; (b) mise à jour du prompt de A pour charger R13 et cesser les mergers; lecture-retour de l'état; (c) création de B à H:25 avec contrat R13 complet; lecture-retour de l'état; (d) vérifier l'activation du duo dans le journal de promotion. Tant que (b)-(c) manquent, R13 est `PENDING_HANDOFF` et aucun nouveau droit d'intégration n'est inféré. Si B est indisponible, A peut développer et produire des DRAFTs, mais aucune mutation merge ne bascule automatiquement vers A: requiert une nouvelle instruction propriétaire cohérente avec main.

## Coordination et anti-collision
- WIP code **global** <=3 PR code ouvertes; comptabiliser toutes les PR code (DRAFT ou non), docs hors WIP mais à compter séparément. Pas de travail doublon ni cinquième branche quand WIP saturé.
- Réserver de façon vérifiable le micro-lot, l'identifiant du ticket, la branche et le rôle writer A/B dans une PR existante ou dans #29 seulement si une mutation de coordination y est autorisée. Les noms des fichiers/ports et les dépendances sont explicites. Un commentaire ou label n'est **pas** un verrou atomique; A/B n'écrivent jamais simultanément sur la même branche. Relecture fraîche de HEAD immédiatement avant chaque mutation et arrêt sur divergence; transfert de writer documenté et vérifiable avant prise en charge.
- Une PR appartenant à A peut être corrigée par B **après transfert explicite de writer** et inversement. Le dernier agent ayant modifié substantiellement le HEAD ne peut pas être son seul contrôleur de revue finale. Les outils partagés sous la même identité GitHub ne fournissent **aucune indépendance GitHub APPROVED**; ne pas fabriquer une approbation. Si une règle du dépôt exige une approbation réellement distincte, attendre cette preuve.
- Chaque exécution finit sur un résultat réel (code, test, CI, décision de revue, correction, ou blocage justifié) et un checkpoint durable: main/base/HEAD, priorité, branche/writer, tests PASS/FAIL/SKIP/NOT_RUN, risque, prochaine action. Aucune tâche n'est présumée travailler en continu entre exécutions.
- La priorité n'est pas un audit perpétuel: débloquer une PR bloquant le chemin critique, puis intégrer les PR qualifiables, puis développer une tranche indépendante. Tests focalisés d'abord; qualifications CI complètes avant fusion sans désactivation de checks.

## Protocole de qualification et fusion — exécutant B seul
1. Premier cycle développe/corrige et ouvre PR DRAFT; **cycle ultérieur distinct** relit adversarialement les changements au HEAD exact, les sources/consommateurs, tests exécutés et contexte. Toute mutation invalide une revue de l'ancien HEAD. Pas d'approbation simulée.
2. B vérifie le même dépôt, l'auteur autorisé, `main`, la branche de base, diff complet (pas seulement le résumé), chemins autorisés, P0/P1 ouverts, reviews/thread bloquants, mergeability, statut non-DRAFT ou passage à ready seulement après revue, G0 + prévol + CPU et Windows/UI pertinents tous `completed/success` sur le HEAD exact. Tests pertinents SKIP = blocage; checks absents ou non lisibles = NO_MERGE.
3. Juste avant fusion B relit `main` et PR, revalide HEAD, CI et checks; utilise squash avec `expected_head_sha`. **Une fusion maximum entre deux débuts d'exécution B consécutifs**. État ou auteur ambigu, requête refusée, défaut d'exclusion mutuelle, changement de base ou HEAD = NO_MERGE sans contournement. A ne merge jamais en période R13.
4. Après chaque fusion vérifier SHA main et workflow G0 push sur exactement ce SHA en `completed/success`; tant que pending/unknown/fail, toutes les autres fusions sont gelées. Un échec entraîne diagnostic, PR de correctif ou de revert revue, sans restauration aveugle.
5. Pas de fusion de PR de gouvernance ou de docs par ces tâches; même si GitHub les permet. Le propriétaire reste décideur des promotions normatives.

## Exigences produit et preuves
- Un writer applicatif de projets, SHA/CAS, masques float32, 4 sorties distinctes (PNG Print Then Cut, SVG Basic Cut, SVG multicouche, SVG d'édition), consentements, non-écrasement, Undo/recovery, vérification unités/mm/viewBox et qualité; conserver les contrats existants.
- Pour une modification: test reproduisant le défaut quand pertinent, au moins trois cas négatifs pertinents, annulation/reprise/concurrence, performance mesurée si impact, tests G0/CPU/Windows nécessaires et rollback. `NOT_RUN` n'est pas PASS.
- GitHub prioritaire pour code/PR/reviews/CI. Context7 uniquement pour documentation officielle correspondant à la version, Superpowers pour méthodes TDD/debug si disponible; Graphify uniquement si SmartSVG indexé prouvé, jamais Titan; Linear/Figma/GitBook seulement si source SmartSVG pertinente vérifiée. Aucune permission/dépense/dépendance externe implicite.

## Mesurer l'accélération
Sur 7 jours d'activité après activation, comparer baseline de 7 jours préactivation (si données réelles accessibles): exigences/DoD réellement intégrées, temps PR vers main, retours de revues, P0/P1, volume de WIP et délais de blocage. Aucun gain fictif. Si l'intégration ralentit ou devient risquée: proposer une correction mesurable, sans auto-éditer la gouvernance.

## Recette de mise en service
Huit cas obligatoires: revendication simultanée d'un même lot; HEAD change après revue; main avance entre review et merge; post-merge G0 FAIL; B indisponible; review externe exigée; WIP code=3; A interrompu après commit. Documenter la prévention et le statut `VERIFIED / NOT_RUN` pour chacun. La recette contractuelle seule ne certifie pas le code ni les plateformes.

**Plan de retour:** désactiver uniquement B via autorisation propriétaire si nécessaire, préserver les branches/PR, mettre à jour la gouvernance et le prompt A de façon cohérente. Ne jamais réactiver la conception, modifier TITAN ou revenir silencieusement à V3.4.
