## 1. Autorité et périmètre

Le propriétaire autorise explicitement la tâche horaire SmartSVG V3.5 déjà existante à soumettre, contre-expertiser puis fusionner **sans validation humaine à chaque PR** les seuls micro-lots de code admissibles. Le second producteur est permis uniquement par l'amendement R13 après gouvernance distincte et passation vérifiées. Cette décision ne change pas la visibilité publique du dépôt ni les règles GitHub; aucune protection de branche, review obligatoire, secret ou droit de dépôt ne peut être contourné. Une revue adversariale par la tâche n'est **pas** une revue GitHub `APPROVED` indépendante.

Un candidat auto-fusionnable doit être une PR vers `main` dans **ce même dépôt** `frenndak/SmartSVG-Studio`, ouverte par le compte propriétaire `frenndak` ou par l'identité d'automatisation déjà autorisée et effectivement vérifiable (ne jamais deviner une identité). Pas de fork, pas de cible extérieure, pas de PR d'auteur inconnu. Branches PR seulement, jamais de push direct sur `main`.

**Chemins autorisés pour l'autofusion :** uniquement du code fonctionnel sous `engine/**`, tests sous `tests/**` ou `engine/tests/**`, scripts techniques locaux sous `tools/**`, et fixtures synthétiques sous `examples/synthetic/**`, **sauf les exceptions suivantes**. Si une PR inclut un seul fichier hors périmètre, elle devient `MANUAL_GOVERNANCE_REVIEW`.

**Chemins et types exclus de l'autofusion, même si un test est vert :** `AGENTS.md`, `.automation/**`, `.github/**`, `docs/**`, `source-releases/**`, fichiers racine, baselines/roadmaps gelées, artefacts ZIP ou binaires, installation/packaging/distribution, `engine/requirements.txt`, dépendances et lockfiles, secrets/jetons, configuration de droits, publication/versionnement, mécanismes d'intégrité/admission et leurs tests (dont `tools/verify_source_integrity.py`, `tools/validate_release_archive.py`, `tools/import_release_archive.py`, `tools/verify_v21152_manifest.py`, `tests/test_governance_owner_delegation.py`, `tests/test_dual_producer_governance_r13.py`, `tests/test_release_archive_gate.py`, `tests/test_release_import.py`, `tests/test_v21152_manifest.py`, `tests/test_private_workflow_routing.py`), ainsi que toute désactivation de contrôle de sécurité, modification de politique, téléversement réseau non prévu ou envoi de données utilisateur vers l'extérieur. Pas de nouvelles dépendances, de changement de format `.smartsvg`, ni d'évolution destructive de contrat sans procédure et approbation distinctes.

Cette autorisation est limitée à **un micro-lot code + éventuellement un correctif directement lié**, avec diff proportionné et tests. Une simple nouvelle interface graphique ne prouve ni la découpe Cricut physique ni une exécution GPU/Windows. Ne jamais certifier ces environnements sans essais réels.

## 2. Protocole en deux cycles distincts

**Cycle A — production :** relire `main`, `AGENTS.md`, `.automation/READY`, ce document, la roadmap V3.5, les PR ouvertes et les issues P0/P1; choisir un lot, créer/mettre à jour une branche et une PR, en DRAFT par défaut, ou directement non-DRAFT quand le connecteur sait créer une PR mais ne peut pas exécuter la transition DRAFT→Ready (voir §2 bis), tests et scénarios négatifs inclus; inscrire dans la PR le ticket, le périmètre, les risques, les commandes/tests et la réversibilité. Aucun merge de ce code pendant le **cycle producteur**.

**Cycle B (ou ultérieur) — contre-expertise adversariale différée :** lors d'une nouvelle exécution du planificateur, relire **depuis GitHub** le diff complet, code consommateur, revue éventuelle, ancien et nouveau `main`, SHA HEAD exact, chevauchements, CI et logs. S'imposer une contre-expertise indépendante de la narration du cycle producteur : rechercher régressions, failles de sécurité, pertes de données, mutations, incohérences de contrat, tests manquants ou fausse confiance. Documenter un verdict factuel (aucune pseudo-approbation `APPROVED`). Seules les PR dont le HEAD reste **identique** après cette contre-expertise sont éligibles. Si correctif/HEAD évolue, recommencer une qualification et un cycle de revue distinct; ne pas réutiliser la revue du HEAD précédent.

**Au plus une PR auto-fusionnée par cycle**, uniquement via `squash`, avec `expected_head_sha` strict et vérification immédiatement préalable du SHA de `main`. Si `main` a changé depuis les preuves, recalculer la mergeabilité, le diff, les tests d'intégration pertinents et le risque; si nécessaire, réconcilier la branche, rerun CI et différer. Ne pas assimiler `behind>0` à un conflit automatique; mais ne pas ignorer les conflits ou la divergence.

### Clarification R13 — revue du SHA réel, sans gel administratif obligatoire (décision propriétaire du 25/11/2026)

Le commentaire `R13_CANDIDATE_FREEZE` est **facultatif et purement informatif**. La qualification repose sur le dernier commit réel de la PR, son HEAD SHA exact, les tests exécutés et une contre-expertise technique par l'autre agent dans un cycle planifié distinct et ultérieur au cycle auteur de ce HEAD. Une revue favorable documentée, faite après le dernier commit dans ce cycle distinct, reste admissible même si un commentaire de gel est absent ou postérieur. Un simple commentaire, changement de label ou mise à jour administrative ne réinitialise jamais cette preuve. Aucun clic humain, accusé de réception supplémentaire ni délai artificiel n'est exigé pour une PR de code admissible lorsque GitHub n'impose pas lui-même une telle condition. Les anciennes candidatures suivent la même règle sans recréation de PR.

Un nouveau commit invalide la revue de l'ancien HEAD et impose une qualification CI et une revue indépendante ultérieure du nouveau SHA. Un changement de `main`, des règles ou des findings impose une requalification des éléments effectivement affectés, notamment du diff, des consommateurs et des tests d'intégration pertinents; aucune réutilisation de preuve devenue invalide. Les preuves immuables complètes peuvent être réutilisées lorsque leur SHA/blob exact est confirmé sur la référence courante; les états mutables et contrôles juste avant fusion sont relus. Ne pas exiger une seconde revue identique uniquement à cause d'un commentaire. Seul B peut fusionner **une seule** PR de code strictement admissible par cycle avec `expected_head_sha` après tous les contrôles §3/§3 bis et preuves Windows pertinentes; le G0 post-fusion reste obligatoire. Une attente CI/revue interdit seulement la fusion du candidat concerné, jamais le travail indépendant autorisé. WIP <=3; une place libre doit servir une tranche utile si aucune revue/correction/fusion n'est actionnable. Les PR documentaires, de format, de sécurité ou de gouvernance restent exclues de l'autofusion. Aucun bypass, désactivation de checks, faux `APPROVED` ou nouveau droit de scheduler.

### 2 bis. PR Ready dès la création si le connecteur ne sait pas lever le brouillon (autorisation propriétaire du 21/11/2026)

**Défaut vérifié :** la mutation GitHub GraphQL `markPullRequestReadyForReview` a été refusée avec `FORBIDDEN` pendant la tentative d'intégration R13 de #179, alors que création de PR, lecture, CI et fusion après transition hors agent ont fonctionné. Ce défaut de permission est une friction de *cycle de vie de PR*, distincte du 403 d'inspection des protections de branche traité en §3 bis. Ne pas supposer que l'une des deux corrections résout l'autre.

**Voie autorisée pour les NOUVELLES PR uniquement :** A ou B peuvent appeler l'API de création GitHub avec `draft=false` dès l'ouverture, après avoir constitué sur leur propre branche un micro-lot cohérent, un diff inspectable, les tests ciblés et une description indiquant honnêtement `REVIEW_PENDING / CI_PENDING / NO_MERGE`. Ce statut permet simplement de demander la revue; **il ne constitue pas une qualification, un APPROVED, une autorisation de fusion ni un PASS**. Les agents ne doivent jamais contourner un refus GitHub : si la création non-DRAFT échoue, classer l'erreur et continuer sur une branche distincte autorisée ou chercher une réparation normale.

Une PR créée non-DRAFT suit les mêmes garanties intégrales que les brouillons : HEAD exact, CI pertinente réelle, contre-expertise adverse **lors d'un cycle ultérieur distinct** par l'autre agent, vérification des règles et reviews GitHub, tous les critères §1–4 et R13, B seul fusionnaire, au plus un squash/cycle, G0 post-fusion PASS avant la suivante. La création non-DRAFT n'implique aucune fusion le jour de sa création. Aucune modification automatique de PR existantes, aucun changement de protections, d'identité ou de permissions.

Pour une PR **déjà DRAFT** que GitHub refuse de passer Ready, l'agent enregistre la preuve du refus **une seule fois** et poursuit un micro-lot indépendant; il ne répète pas la même tentative aveugle à chaque cycle et ne ferme/recrée pas automatiquement la PR pour éviter l'autorisation manquante. Un responsable disposant des droits ordinaires peut effectuer la transition; la PR conserve toutes ses garanties.

## 3. Conditions bloquantes avant chaque fusion (fail-closed)

Toutes les conditions doivent être **démontrées**, pas inférées :
1. Autorité actuelle : `AGENTS.md` et `.automation/READY` concordants, opt-in exact activé, dépôt public attendu, aucun stop propriétaire, aucune règle GitHub inconnue à contourner.
2. PR admissible selon §1; HEAD SHA complet et base `main` courants, état `mergeable=true` confirmé après rafraîchissement, revue GitHub sans `CHANGES_REQUESTED` non résolu, aucune exigence de review obligatoire non satisfaite. Vérifier les règles effectives selon **§3 bis** : une API de détail protection qui renvoie 403 n'est PAS une preuve de l'absence de protection, et n'est pas non plus à elle seule une preuve de son existence. Une erreur de fusion GitHub ou une règle inconnue bloque toujours.
3. Aucun défaut connu P0/P1 non résolu touchant la PR, aucun secret/donnée privée, suppression de test, assertion affaiblie, check supprimé, fichier protégé, changement destructif ni diffusion non prévue.
4. Preuve CI sur le HEAD exact : **G0 Admission Tests** `completed/success`, **Public read-only preflight** `completed/success`, tous les jobs requis/relevants `completed/success` avec étapes obligatoires exécutées. Une conclusion `success` contenant un test pertinent `SKIPPED` n'est PAS un PASS; rechercher dans logs/steps la commande et le cas vraiment exécutés. Pour tout changement `engine/**` ou nécessitant CPU, exiger `Live Engine CPU Smoke` `completed/success`, et tests fonctionnels ciblés réellement réussis (NumPy/Pillow si nécessaires); aucune validation runtime seulement théorique. Un `skipped` admis dans G0 n'est couvert que si **le même test** est effectivement PASS dans un autre job sur le même HEAD.
5. Une PR portant seulement sur `tests/**` ou `tools/**` nécessite des tests ciblés pertinents et des workflows réellement déclenchés pour ce HEAD; pas de passe-droit parce qu'un workflow n'a pas été programmé. `QUEUED/PENDING/CANCELLED/TIMED_OUT/FAILURE/UNKNOWN` interdisent la fusion.
6. Réversibilité : squash clairement identifié, procédure de revert par PR et risque de données évalué. Ne pas fusionner un changement irréversible ou une migration exigeant sauvegarde sans l'autorisation distincte nécessaire.

**Toute condition absente = NO_MERGE**, classifier `NEEDS_CI`, `FIX_REQUIRED`, `MANUAL_GOVERNANCE_REVIEW`, `BLOCKED_GITHUB_PROTECTION` ou `UNVERIFIED`. Ne jamais utiliser admin bypass, force-push sur main, auto-approve, token alternatif, changement de règles, fausse CI ou suppression de tests pour accélérer.


### 3 bis. Lecture alternative des règles GitHub si l'endpoint protection répond 403 (amendement propriétaire 2026-11-21)

**Constat vérifié :** sur le dépôt public personnel `frenndak/SmartSVG-Studio`, `GET /repos/{owner}/{repo}/branches/main/protection` peut retourner `403 Resource not accessible by integration` parce que l'application ne dispose pas du droit GitHub **Administration:read** exigé par cet endpoint. Ce 403 est une **limite du jeton**, pas une réponse booléenne sur la protection. On ne l'efface pas et on ne le présente jamais comme preuve `unprotected`.

Pour ce dépôt et **seulement** lorsque l'endpoint détaillé est inaccessible, une lecture alternative est **admissible** sous ces conditions **cumulatives, fraîches et documentées sur le même `main`** :

1. `GET /repos/frenndak/SmartSVG-Studio/branches/main` répond avec `name=main`, `commit.sha` exact et `protected === false` (booléen GitHub réel, non déduit d'un statut CI ou d'un texte). Cet indicateur GitHub incorpore la protection classique **et** les rulesets. `true`, champ absent, valeur ambiguë, réponse périmée ou appel en erreur => **NO_MERGE** jusqu'à lecture explicite des règles correspondantes et des exigences applicables.
2. `GET /repos/frenndak/SmartSVG-Studio/rulesets?includes_parents=true&per_page=100` répond `200` avec liste **complète** vide `[]`; suivre toutes les pages/pagination disponibles avant de conclure. Liste non vide (même evaluate/disabled si effet incertain), erreur ou résultat tronqué => **NO_MERGE** jusqu'à qualification complète des rulesets. Sur un dépôt devenu propriété d'une organisation ou transféré, ne pas réutiliser la preuve historique du compte personnel.
3. La même identité connectée doit pouvoir lire la PR courante `draft=false`, `mergeable=true`, HEAD SHA exact, auteur autorisé et absence de review `CHANGES_REQUESTED` / threads non résolus; vérification CI, fichier, revue adverse différée et toutes les exclusions des §1–4 **inchangées**. Une revue technique par A/B ne peut pas produire un vrai `APPROVED` exigé par GitHub; une protection positive exige l'approbation réelle.
4. Après les vérifications précédentes, **B uniquement** peut demander un unique squash `merge_pull_request(expected_head_sha=HEAD)`, **sans bypass**, sans `admin`, sans `force`, sans mise à jour/suppression de règles et sans push direct. **Toute réponse GitHub refusant la fusion** (403/405/409/422, contrôle/review manquant, erreur de droits) => **BLOCKED_GITHUB_PROTECTION**, ne jamais réessayer avec des droits/identités alternatives pour contourner. Le G0 post-fusion exact-`main` reste obligatoire.

L'absence de protection est donc **établie uniquement par les deux signaux GitHub positifs `protected:false` et rulesets `[]`** consultés à nouveau immédiatement avant la fusion, **jamais** par le 403, par `rulesets=[]` seul ou par la permission de dépôt `admin=true`. Si les sources se contredisent ou si un endpoint requis manque, **NO_MERGE**. GitHub applique toujours ses règles serveur. Aucun contrôle métier, dépendance, revue ni mesure de sécurité n'est relâché. Ce changement est une **modification de gouvernance autorisée en session propriétaire** et ne peut jamais être produit ou fusionné par les tâches planifiées.

## 4. Post-fusion et anti-embouteillage

Après fusion, revérifier GitHub `closed+merged`, SHA du nouveau `main`, et lancement puis verdict du **G0 push post-merge** sur le SHA de `main` (et autres checks pertinents disponibles). Tant que ce verdict reste `pending`, ne pas fusionner une autre PR. S'il échoue, **geler les intégrations** et examiner la cause ; préparer un revert sur branche/PR avec CI et contrôle des changements intervenus, sans annuler en aveugle des données utilisateur ni contourner les protections. Une PR de revert qui traverse un chemin protégé exige revue de gouvernance distincte.

En cas de WIP>=4, qualifier les PR existantes et intégrer au plus une PR admissible plutôt que déclarer une impasse. Les PR non admissibles reçoivent un motif précis et une réparation reproductible, sans commentaire identique répété. En cas de panne DNS/git locale, utiliser les connecteurs GitHub pour inspecter les SHAs, diffs et logs; ne pas prétendre exécuter NumPy ou une suite locale si seul le connecteur est disponible.

Noter dans l'issue de coordination #29 **uniquement un changement matériel** : PR/HEAD/base, tests réellement exécutés et `SKIPPED`, checks exact-head, verdict hostile, merge/revert SHA, résultat G0 post-merge, statut du lot `SPECIFIE/IMPLEMENTE/TESTE/INTEGRE`, prochain lot. Ne jamais clore automatiquement une issue plus large que la tranche livrée.

## 5. Désactivation et réversibilité

Le propriétaire peut révoquer l'opt-in en retirant `AUTONOMOUS_MERGE_V35=ENABLED` de `.automation/READY` via une modification de gouvernance autorisée, ou en arrêtant la tâche planifiée. Une contradiction entre sources rétablit immédiatement DRAFT-only. Une modification de ce document ou de la gouvernance elle-même est **toujours exclue** de l'autofusion; elle exige une session propriétaire spécifique. Ce protocole n'installe à lui seul ni privilège ni tâche; la création de B est une étape distincte après la promotion R13.

## 6. Amendement propriétaire R13 — deux producteurs, fusionnaire unique

Cette section remplace seulement les clauses R1/R12 incompatibles concernant le producteur unique et le droit de fusion de A. Les chemins interdits, tests, revue différée et contrôles complets restent inchangés. Consulter [le contrat R13](roadmap-v3.5/DUAL_PRODUCER_R13_CONTRACT.md). Conditions cumulatives: AGENTS sur main concordant, READY avec une seule occurrence des quatre marqueurs V34=DISABLED, V35=ENABLED, DUAL_PRODUCER_V35=AUTHORIZED et R13_MERGE_EXECUTOR=AGENT_B, PR de gouvernance revue et intégrée par le propriétaire, G0 push sur SHA exact main PASS, prompt A R13 et nouvelle tâche B lus après activation. Sinon **NO_MERGE / DRAFT-only**.

**A** H:55: produit, teste, corrige, contre-expertise, soumet des PR, mais ne fusionne plus après passation R13. **B** H:25: qualifie, contre-expertise, corrige, teste, peut développer des tranches réellement indépendantes et devient l'unique exécuteur d'API merge. Autorisation de merge de A ne réapparaît jamais automatiquement si B est indisponible. Les agents ne peuvent pas intervenir simultanément sur la même branche: transfert documenté de writer et relecture HEAD avant chaque écriture. Un commentaire, label ou timestamp n'est pas un verrou atomique. WIP code <=3 global, une tranche + correctif lié par itération.

B respecte une **revue adverse sur un cycle ultérieur** sur le diff complet et HEAD exact; nouveau commit => nouvelle revue, aucun APPROVED fictif. Un agent ne peut être seul réviseur de son propre correctif; l'utilisation de la même identité GitHub par A/B ne satisfait pas une approbation GitHub externe obligatoire. Avant un squash, B relit la branche, main, l'auteur, l'ensemble des fichiers, reviews bloquantes, mergeability, G0/prévol/CPU/Windows pertinents completed/success au SHA exact, aucun test pertinent SKIP, aucune P0/P1. `expected_head_sha` obligatoire. Une fusion maximum dans la fenêtre entre deux débuts de cycle B. Tant que le G0 push exact SHA post-merge est pending/failed/unavailable, toute autre fusion est bloquée. Aucun bypass GitHub.

Le but est de livrer des capacités utiles: qualifier/intégrer les PR bloquées, résoudre leur problème reproductible, puis avancer sur un lot indépendant. Les audits génériques répétés n'ont pas priorité sur une action concrète. Aucune modification de docs, AGENTS, READY, .github, dépendances, packaging, contrôles d'admission/permissions ou publication depuis les tâches. La tâche historique de conception reste arrêtée.
